## 3. Gaps verificáveis

### 3.1 Banco

1. `relationship_status` ainda aceita `lead` e `prospect`; o contrato E4 exige escrever somente
   `new_lead` e `known_lead`, com transição compatível e backfill controlado.
2. `contacts` não possui `primary_email`, `owner_user_id`, `merged_into_contact_id`,
   `archived_at`, `classification_source`, `classification_confidence` nem
   `last_qualified_at`.
3. Não existem `contact_merge_events`, `contact_consents`, `contact_external_refs` ou
   `contact_segments`.
4. `contact_touchpoints.landing_page_id` é `text`; a spec pede ID canônico UUID, preservando o
   valor legado durante o backfill.
5. Não há catálogo `lead_sources` autoritativo para slug, domínio/origens permitidas e hash do
   token de captura.
6. `source_kind` não possui CHECK fechado e os campos de UTM/referrer não têm contrato próprio;
   metadata livre não pode ser aceita como substituto sem allowlist.
7. A unicidade de touchpoint é `(account_id, provider, external_event_id)` somente quando o
   external id é não nulo. Eventos de landing/manual precisam de uma idempotency key explícita.
8. Não há índice parcial case-insensitive para email, índice de owner/status ou índice comprovado
   para os filtros de CRM; qualquer índice novo deve vir acompanhado de `EXPLAIN` representativo.

### 3.2 Backend e API

1. `GET /v1/omnichannel/contacts` devolve a lista inteira, sem cursor, busca, filtros por canal,
   status, tag, owner ou origem.
2. O único perfil é a projeção de `ContactView`; não existe endpoint 360° com identities,
   touchpoints, notas e timeline paginadas.
3. Há somente criar/listar/atualizar contato. Não existem endpoints de notas, merge/undo,
   candidatos de conflito, segmentos, exportação, confirmação ERP ou captura de landing page.
4. `CreateContact` ainda exige telefone e faz upsert por `(account_id, phone)`, portanto não
   atende perfis Instagram sem telefone nem a ordem completa de resolução de identidade.
5. O inbound procura primeiro telefone e, sem telefone, identidade externa; não há etapa de
   email verificado, detecção de múltiplos candidatos ou fila de conflito.
6. O touchpoint de mensagem usa `source_kind = direct_message`, que ainda não está no catálogo
   fechado da spec (`whatsapp_inbound`, `instagram_dm`, etc.).
7. A resposta de classificação ainda não tem fonte/confiança CRM persistidas; a IA não pode
   sobrescrever uma classificação manual ou confirmada por ERP.

### 3.3 Frontend

1. O inbox possui uma lista básica de contatos, mas não há tela 360° dedicada.
2. Não há UI para identities, touchpoints, lifecycle, owner, consentimentos, campos customizados,
   notas paginadas, merge, conflitos, segmentos, exportação ou confirmação ERP.
3. Os filtros atuais do inbox não constituem o contrato de busca/segmentação do CRM e não devem ser
   reaproveitados como fonte de verdade.

## 4. Contrato final congelado para os próximos pacotes

- conta é sempre derivada do `Principal`; nenhum body/query fornece autoridade de tenant;
- resolução: identidade exata → telefone E.164 confiável → email verificado → novo contato;
  múltiplos candidatos geram conflito, nunca auto-merge;
- `relationship_status` canônico: `new_lead`, `known_lead`, `customer`, `inactive`;
- precedência de classificação: ERP/fonte comercial confirmada > alteração manual > regra > IA >
  backfill;
- touchpoints são idempotentes, tenant-scoped e registram primeira/última interação monotônicas;
- merge move identities, conversations, notes e touchpoints em uma transação, salva snapshot e
  permite undo somente quando o snapshot ainda for reversível;
- token de landing page é armazenado somente como hash; origem e conta são resolvidas no servidor;
- logs nunca exibem telefone/email completos, token, captura ou metadata bruta.
