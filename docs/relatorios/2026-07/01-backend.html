Visão geral

API monolítica em Go organizada em módulos plugáveis. É a peça mais madura do produto: padrão de arquitetura consistente em 20 módulos, segurança de entrada bem resolvida e CI que de fato roda os testes. As dívidas são pontuais e conhecidas — cache de autenticação desligado, listagens sem paginação e alguns arquivos gigantes.

Veredito: arquitetura modular sólida e consistente — o mesmo esqueleto module.go / http.go / service.go / store_postgres.go se repete em todos os módulos, com AGENT.md documentando cada um. A base de segurança (queries parametrizadas, JSON estrito, headers completos) é acima da média para o estágio do produto. O que pesa contra: o PrincipalCache existe mas está desligado (1 query extra em cada request autenticado — AC-01), três famílias de listagem sem paginação (AC-06) e uma minoria de arquivos muito acima do teto de 450 linhas (AC-13).

Stack

  • Go 1.24 — binário único, net/http puro com rotas method-pattern (sem framework)
  • pgx/v5 — acesso direto ao PostgreSQL via pool, sem ORM
  • gorilla/websocket — hub realtime in-memory (presença, eventos de operação/tasks)
  • JWT HMAC-SHA256 + bcrypt — sessões persistidas em core.user_sessions com revogação server-side
  • slog — logs estruturados para stdout (coletados via docker logs)

Módulos

O backend é um monólito modular: cada domínio vive em back/internal/modules/<nome> e se registra num Module Registry central que monta rotas e event handlers. Os 20 módulos somam ~89.101 linhas (média ~4.455/módulo) — o restante das 93.657 linhas fica na plataforma (httpapi, app, database, events).

Anatomia de um módulo

2

3

AGENT.md — contrato do módulo para humanos e agentes: escopo, responsabilidades e regras. Existe em todos os módulos e é mantido junto com o código

Tempo real (realtime)

  • gorilla/websocket: writeWait 10s, pongWait 60s, ping 54s, mensagem máx. 1.024 bytes
  • CheckOrigin valida contra a whitelist de CORS — não aceita origem arbitrária
  • Hub e presença (TTL 30s) são in-memory — funciona em 1 instância; escalar exige pub/sub (ver AC-08)
  • SSE público no bio: /v1/public/bio/{slug}/stream

Superfície pública (sem auth)

  • /v1/public/bio/{slug}/config|stream — consumida pelo front crow-nuxt
  • /v1/public/cardapio/{slug}/catalog|orders — consumida pelo TAVOLA, com rate limit
  • /v1/auth/gateway/verify — SSO via forward_auth do Caddy (platform_admin)

Pontos críticos

Seis achados canônicos tocam o backend — cinco detalhados abaixo; o sexto (AC-10, refresh token) está no backlog da aba Oportunidades. Nenhum é incêndio de segurança; o P0 é uma dívida de performance com correção pequena e retorno em toda requisição autenticada do sistema.

P0  AC-01 — PrincipalCache implementado mas desligado

O cache de principal está pronto em httpapi/principal_cache.go:24, com interface em auth/service.go:12 e o setter SetPrincipalCache na linha 59 — mas zero chamadas fora de testes: nada em app.go liga o cache. O próprio auth/AGENT.md:97 confirma o estado. Consequência prática: Authenticate consulta IsRevoked no banco a cada request autenticado. Como todo o painel é autenticado, isso é 1 query extra em praticamente 100% do tráfego — a query mais executada do sistema é uma checagem que quase nunca muda de resposta. O detalhe que dói: a infraestrutura de invalidação já existe (eventos user.session.revoked e role.permissions.changed no bus) — falta só o wiring. Esforço S, impacto alto. Ver também 05-Performance e a página 07.

P1  AC-06 — Listagens sem paginação (reports, analytics, BI)

  • Reports: listHistoryQuery não tem LIMIT/OFFSET (queue/reports/store_postgres.go:39-150) e serve /v1/reports/overview|results|recent-services — o histórico inteiro da loja vem do banco a cada chamada
  • Analytics: loadServiceHistory carrega o histórico COMPLETO da loja sem LIMIT (queue/operations/store_postgres.go:565-617) para alimentar /v1/analytics/ranking|data|intelligence
  • BI: /v1/bi/perola/overview devolve até 5.000 registros por dataset num payload único — pageLimit=100 × maxPages=50 (bi/service.go:23-24)

Hoje funciona porque as lojas são pequenas; o custo cresce linear com o histórico e a conta chega junto com o sucesso do produto. Correção: LIMIT/OFFSET ou cursor + agregação no SQL, com teto por página. Esforço M, impacto alto. Ver também 03-Banco de dados e 05-Performance.

P2  AC-13 — Arquivos Go gigantes

Os cinco maiores arquivos: bi/service.go 1.739, queue/operations/store_postgres.go 961, queue/alerts/service.go 831, crm/erp/model.go 798 e realtime/service_tasks.go 792 — a medição aponta 4 dos 5 acima do teto de 450 linhas dos princípios de engenharia do projeto. É exceção, não regra (485 arquivos no total), mas o bi/service.go em quase 4× o teto merece um split em subpacotes (client, aggregator, filter). Os demais entram na manutenção normal.

P2  AC-08 — Caches em memória local

Quatro caches vivem no processo: goal progress (TTL 120s), module guard (60s), image cache do site e os buckets do rate limit. Em 1 instância, funciona bem e é rápido. O problema aparece no scale-out: uma 2ª instância teria caches e limites inconsistentes entre si (um usuário pode ser limitado numa instância e não na outra; módulo desabilitado pode continuar ativo até o TTL da outra). Não é bug hoje — é um pré-requisito documentado do cenário de escala: abstrair atrás de interface e mover para Redis quando for a hora. Ver também 05-Performance, 07 e 09.

P2  AC-09 — Guard do dev secret: existe, mas só para production exato

A história certa, em ordem: o briefing inicial desta série afirmava que o secret default de desenvolvimento (devTokenSecretDefault="dev-secret-change-me", config.go:12) podia ir para produção sem nenhuma proteção. A verificação provou que a proteção existe: Validate() (config.go:193-208) rejeita o secret default quando Env=="production" (linha 199), e há teste cobrindo isso (config_test.go:75-82). O que sobra de risco é a comparação exata com a string production: um operador que configure APP_ENV=prod ou staging passa pelo guard com o secret default — e JWT HMAC com secret conhecido significa forjar token de qualquer usuário. Correção fail-closed simples: validar sempre que Env != development/test. Ver também 06-Segurança.

⚠️ O que NÃO apareceu aqui: não foi encontrada concatenação de SQL, parse de JSON permissivo ou rota autenticada sem middleware. Os críticos do backend são de performance e operação, não de correção — um perfil raro e positivo para um produto nesta fase.

Oportunidades de melhoria

Backlog priorizado do backend. P0 = agir já · P1 = próximas semanas · P2 = quando escalar. Achados AC-* são canônicos da série (id, prioridade e evidência fixos); BE-* são locais desta página.

AC-01PrincipalCache implementado mas desligado — auth consulta o banco a cada requestP0Esforço: SImpacto: alto›

Problema: o cache de principal está codificado e testado, mas nada o liga no boot — Authenticate faz a query IsRevoked em toda requisição autenticada, tornando a checagem de sessão a query mais executada do sistema.

Evidência: httpapi/principal_cache.go:24 + auth/AGENT.md:97; zero wiring em app.go (nenhuma chamada a SetPrincipalCache fora de testes).

Ação recomendada: ligar o cache com TTL curto + invalidação pelos eventos realtime já existentes (user.session.revoked, role.permissions.changed). Ver também 05-Performance e página 07.

AC-06Listagens sem paginação (reports, analytics, BI)P1Esforço: MImpacto: alto›

Problema: três famílias de endpoint carregam o histórico completo do banco em cada chamada; o custo cresce linear com o volume de atendimentos e datasets.

Evidência: queue/reports/store_postgres.go:39-150 sem LIMIT; queue/operations/store_postgres.go:565-617 histórico completo da loja; BI até 5.000 registros por payload (bi/service.go:23-24, pageLimit=100 × maxPages=50).

Ação recomendada: LIMIT/OFFSET ou cursor + agregação no SQL; teto por página. Ver também 03-Banco de dados e 05-Performance.

Problema: uma minoria de arquivos concentra responsabilidade demais e fura o teto de 450 linhas dos princípios de engenharia do projeto, dificultando revisão e manutenção.

Evidência: bi/service.go 1.739 linhas; queue/operations/store_postgres.go 961; queue/alerts/service.go 831; crm/erp/model.go 798.

AC-09Guard do dev secret só dispara com APP_ENV exatamente 'production'P2Esforço: SImpacto: médio›

Problema: a proteção contra subir com o secret JWT default existe e tem teste — mas compara a string exata production; ambientes nomeados prod ou staging passam com o secret default, o que permitiria forjar tokens.

Evidência: config.go:193-208 (guard existe e tem teste em config_test.go:75-82); 'prod'/'staging' passam com secret default.

AC-08Caches e rate limit em memória local — travam scale-out horizontalP2Esforço: MImpacto: alto (na escala)›

Problema: caches de goal progress (120s), module guard (60s), image cache e buckets de rate limit vivem no processo; uma 2ª instância da API teria estado inconsistente (limites e gating divergentes entre réplicas).

Evidência: goal progress 120s, module guard 60s, rate limit buckets — todos in-process; 2ª instância = inconsistência.

Ação recomendada: abstrair atrás de interface e mover para Redis quando for escalar — é pré-requisito de software do cenário Escala. Ver também 05-Performance, 07 e 09.

BE-01Sem OpenAPI/spec das ~377 rotasP2Esforço: MImpacto: médio›

Problema: o contrato da API vive apenas no código (method-patterns em http.go) e nos AGENT.md por módulo. Sem uma spec formal, qualquer integração externa (automação n8n, fronts separados TAVOLA/crow-nuxt, futuros clientes) depende de ler código Go, e mudanças de payload não têm validação de contrato.

Evidência: ~377 rotas method-pattern medidas por grep em back/internal; nenhum arquivo openapi/swagger no repositório.

Ação recomendada: começar pequeno — especificar primeiro a superfície pública (/v1/public/*) e as rotas consumidas pela automação; gerar/validar via CI depois. Não precisa ser big-bang das 377.

AC-10Sem refresh token (sessão de 12h, logout só server-side)P2Esforço: MImpacto: médio›

Problema: o access token JWT vive ~12h sem mecanismo de renovação; encurtar o TTL hoje significa deslogar usuários no meio da operação, então o TTL longo compensa a ausência de refresh — trade-off que aumenta a janela de uso de um token vazado.

Evidência: auth/tokens.go; TTL via AUTH_TOKEN_TTL (~12h); sessões revogáveis em core.user_sessions (logout → 401).

Ação recomendada: refresh token rotativo + encurtar o TTL do access. Achado canônico da série, detalhado em 06-Segurança — registrado aqui porque a implementação é no módulo auth.
