Visão geral

O frontend do Omni é um painel SPA único que concentra 13+ domínios de produto (operação realtime, CRM/ERP, tasks, cardápio, calendário com IA, meta ads, financeiro…). É grande, funcional e com decisões de engenharia acima da média para o estágio — mas carrega dívida clara de tamanho de arquivo e de cobertura de testes.

Veredito: front funcional e rico em features, com fundações boas (api-client com dedupe, permissões fail-closed, lazy loading real com retry) — mas 105 arquivos acima do teto de 450 linhas e apenas 17 arquivos de teste para 313 componentes tornam a manutenção cada vez mais cara. A dívida é de disciplina, não de arquitetura.

Stack

  • Nuxt 4.4.2 — 100% SPA: 39 routeRules com ssr:false; o painel inteiro é client-rendered por decisão explícita (bootstrap de auth no servidor era frágil no hard reload).
  • Vue 3 + Pinia 3.0.4 — 37 stores de código + 61 composables.
  • Tailwind 4.3 + Nuxt UI 4.7.1 — utilitários + biblioteca de componentes, complementados por CSS próprio (ver aba Design).
  • TipTap 3 (editor rico) e ApexCharts 5 (gráficos BI/analytics).
  • Vitest 2.1.9 — instalado e no CI, mas subutilizado (17 arquivos de teste).
  • Node 24.11.1 no ambiente de build.

Leitura rápida

  • Comunicação com a API centralizada num único cliente (api-client.ts, 331 linhas) — sem fetch espalhado.
  • Realtime via WebSocket com composables dedicados; polling só onde faz sentido (IA do calendário, feedback).
  • Gating de permissão fail-closed com 28 workspaces mapeados.
  • BFF Nitro mock de finance ainda vivo em web/server/ — única parte do front que não fala com o banco real (AC-12).
  • 105 arquivos acima de 450 linhas (AC-07) e cobertura de teste baixa (AC-15).
💡 Metodologia: todos os números desta página vêm de medição local em 2026-07-02 (branch refactor/multitenant-complete, working tree com mudanças não commitadas). Descrições qualitativas foram conferidas lendo o código-fonte. Nada aqui é medição de produção.

Arquitetura

Nuxt Layers para os domínios maiores + um app/ central organizado por domínio. Toda a comunicação com o backend Go passa por um cliente único; o realtime tem camada própria de composables sobre WebSocket.

Camadas (4 Nuxt Layers + app/)

1
layers/core — autenticação, tema (useOmniTheme/useThemeStudio), administração e componentes base compartilhados. É a fundação que as demais camadas estendem.
2
layers/queue — fila de atendimento / operação (o domínio original do produto).
3
layers/tasks — kanban de tarefas, com páginas e stores próprios (inclui os 4 únicos arquivos de teste fora do app/).
4
layers/finance — financeiro; hoje ainda alimentado pelo BFF mock (ver AC-12 abaixo).
5
app/ — 49 páginas, componentes organizados por domínio (components/calendar/, components/crm/, components/roadmap/…), 37 stores Pinia, 61 composables e um diretório domain/ com lógica pura (permissões, api de calendário etc.), separada da UI.

Permissões no front

  • domain/utils/permissions.ts — 916 linhas, 28 workspaces com view/editPermission, papéis de consultant a platform_admin.
  • Gating fail-closed por módulo: sem permissão explícita = sem acesso, alinhado ao RBAC do backend.
  • Padrão obrigatório isPlatformAdmin || has(...) em todo menu/seção: has() retorna false para o platform_admin (que não tem permissões granulares), então esquecer o curto-circuito faz a UI sumir para o admin. É convenção manual — não há lint que garanta.

AC-12 — BFF mock de finance ainda vivo P1

10 arquivos em web/server/, todos de finance; o restante do BFF já foi removido conforme o ADR 0002. Rotas Nitro servidas de um store em memória (financeMockStore.ts) — dados somem no restart e não existem no banco:

  • GET/PUT /api/admin/finance-config
  • GET /api/admin/finance-config/recurring-clients
  • GET/POST /api/admin/finance-sheets
  • GET/PUT/DELETE /api/admin/finance-sheets/[id]
  • PATCH /api/admin/finance-sheets/[id]/lines/[lineId]

Ação: portar finance para a API Go e apagar web/server/. Ver também o relatório 07.

💡 A decisão de SPA total (39 ssr:false em nuxt.config.ts) é documentada no próprio config: rota de painel fora da lista roda SSR e o bootstrap de auth no servidor deslogava/estourava no hard reload. O efeito colateral é que toda rota nova precisa ser adicionada manualmente — e há um caso recente escapando (FE-03, aba Oportunidades).

Bugs conhecidos de tema (verificados)

  • Tema liquidglass rejeitado pelo back: a whitelist de normalizeAppearanceTheme aceita só light | dark | apple | custom (back/internal/modules/queue/settings/sections.go:207-217), enquanto os tokens do front definem apple-blue e liquidglass. Salvar a aparência com liquidglass cai silenciosamente no fallback. Vira FE-01.
  • Aparência do platform_admin sem tenant só em localStorage: sem tenant ativo, a preferência de tema do admin não persiste no banco — troca de navegador/máquina perde a escolha. Vira FE-02.
  • Há trabalho em andamento na working tree (core/platform_appearance_*, não commitado) cujo comentário indica a intenção de temas novos não exigirem deploy do back — endereçaria a causa raiz do item acima.

Relação com Tailwind / Nuxt UI

O CSS próprio não compete com o Tailwind: os tokens em omni-tokens.css definem a identidade (cores, superfícies, temas) e os arquivos por domínio cobrem componentes complexos (calendário, modais, apresentação) onde utility-first ficaria ilegível. O risco real é o components.css: 4.480 linhas num arquivo só significam que qualquer ajuste visual exige buscar seletores num monólito, e estilos mortos não são detectáveis. A recomendação do AC-07 (ver aba Oportunidades) inclui fatiá-lo por domínio, seguindo o exemplo já dado pelo diretório calendar/.

AC-15 — Cobertura de testes P1

  • 17 arquivos .test.ts no front inteiro (zero .spec.ts) contra 313 componentes, 37 stores e 61 composables.
  • Comparação interna: o backend Go tem 65 arquivos de teste com 12.188 linhas (13% do código) — o front está muito atrás do próprio padrão do repo.
  • O que existe está bem posicionado: entre os testados estão useContextRealtime e useOperationsRealtime (o coração do realtime da operação) e stores.
  • Maior retorno por esforço: stores e domain/utils (lógica pura, sem DOM) primeiro; componentes críticos da operação depois.

Pontos fortes de engenharia OK

  • Lazy loading real com tratamento de falha: utils/lazy-component.ts embrulha defineAsyncComponent com retry automático, timeout e errorComponent acionável ("Recarregar") — resposta direta ao incidente do "modal em branco em produção" (chunk 404 pós-deploy). Aplicado a 5 componentes pesados: OperationWorkspace, MetaAdsReportChart, CardapioAnalyticsChart, RoadmapModulesBoard e OmniEditor.
  • Dev experience deliberada: vite.optimizeDeps com 14 deps pré-bundladas, warmup de 7 arquivos do shell e watcher chokidar granular com polling para o cenário Docker + Windows.
  • Sem manualChunks: o split de bundle é o default por rota do Vite; nunca houve análise de bundle para saber se o vendor está saudável (FE-04).

Nota da área

6,5
Arquitetura e fundações acima da média (camada de API única, permissões fail-closed, lazy com retry, realtime estruturado), puxadas para baixo por dívida objetiva e mensurável: 105 arquivos fora do teto, 17 testes para 313 componentes e um mock de finance ainda em produção de código. Oportunidades de melhoria

Backlog priorizado da área. P0 = agir já · P1 = próximas semanas · P2 = quando escalar. AC-* são achados canônicos da série (mesmo id/prioridade em todos os relatórios); FE-* são achados locais desta página.

AC-07105 arquivos front acima de 450 linhas + components.css monolítico (4.480)P1Esforço: LImpacto: médio›

Problema: o teto de 450 linhas por arquivo é regra escrita dos princípios de engenharia do projeto, e 105 arquivos a violam — com casos extremos de 3.029 linhas num composable. Arquivos gigantes concentram risco: toda mudança tem raio de explosão máximo, review fica superficial e o Vite recompila blocos enormes no dev.

Evidência: medição wc -l de 2026-07-02 — top: useTasksPageContext.ts 3.029, roadmap-data.ts 2.614 (majoritariamente dado declarativo), MultiStoreGoalsSection.vue 2.334; CSS: web/app/assets/styles/components.css 4.480 linhas.

Ação recomendada: quebrar primeiro os arquivos >1.000 linhas; fatiar components.css por domínio (o diretório calendar/ já mostra o padrão); adicionar regra de tamanho no lint-staged para estancar o crescimento. Ver também o relatório 07.

AC-15Cobertura de testes do front baixa (17 arquivos para 313 componentes)P1Esforço: LImpacto: médio›

Problema: com 17 arquivos .test.ts para 313 componentes, 37 stores e 61 composables, quase toda regressão só é descoberta manualmente. O Vitest já roda como gate no CI — a infraestrutura existe, faltam os testes.

Evidência: 17 .test.ts (13 em app, 4 em layers/tasks), zero .spec.ts; comparação interna: o back tem 65 arquivos de teste / 12.188 linhas (13% do código Go).

Ação recomendada: começar por stores e domain/utils (lógica pura, maior retorno por esforço — permissions.ts com 916 linhas é o candidato nº 1); depois componentes críticos da operação. Ver também o relatório 07.

AC-12BFF mock de finance ainda vivo em web/server/P1Esforço: MImpacto: médio›

Problema: o módulo financeiro do painel opera sobre um store em memória do Nitro — os dados não existem no banco real, somem no restart e violam o princípio de fonte única de verdade do projeto. O ADR 0002 já determina a remoção; o resto do BFF foi eliminado, só finance sobrou.

Evidência: 10 arquivos em web/server/: 9 handlers (GET/PUT /api/admin/finance-config, GET .../recurring-clients, GET/POST /api/admin/finance-sheets, GET/PUT/DELETE .../[id], PATCH .../[id]/lines/[lineId]) + web/server/utils/financeMockStore.ts.

Ação recomendada: portar finance para a API Go (módulo + migrations) e apagar web/server/ inteiro. Ver também o relatório 07.

FE-01Tema liquidglass rejeitado pela whitelist do backP2Esforço: SImpacto: baixo›

Problema: o front oferece 4 temas (light, dark, apple-blue, liquidglass em omni-tokens.css), mas o normalizador de aparência do back só aceita light | dark | apple | custom. Salvar a aparência com liquidglass cai silenciosamente no fallback — o usuário escolhe um tema que não persiste, sem nenhum aviso.

Evidência: back/internal/modules/queue/settings/sections.go:207-217 (switch com a whitelist) vs. os 4 temas de web/app/assets/styles/omni-tokens.css.

Ação recomendada: incluir os identificadores reais dos temas do front na whitelist (ou adotar o desenho em andamento em core/platform_appearance_*, cujo comentário já prevê temas novos sem deploy do back). Exigirá rebuild da api.

FE-02Aparência do platform_admin sem tenant só persiste em localStorageP2Esforço: SImpacto: baixo›

Problema: a persistência de aparência é escopada por tenant; o platform_admin navegando sem tenant ativo tem a preferência salva apenas em localStorage. Trocar de navegador ou máquina perde o tema — inconsistente com o comportamento dos demais usuários.

Evidência: bug conhecido verificado em 2026-07-02 (composables de tema em web/layers/core/composables/useOmniTheme.ts / useThemeStudio.ts); o trabalho não commitado em back/internal/modules/core/platform_appearance_* na working tree indica que a correção já está em andamento.

Ação recomendada: persistir a aparência de plataforma (sem tenant) no banco via endpoint dedicado — concluir e commitar o trabalho já iniciado.

FE-03routeRule de /calendario não cobre a nova subrota /calendario/configP2Esforço: SImpacto: médio›

Problema: pages/calendario.vue foi deletado e virou diretório (pages/calendario/index.vue + config.vue). A rota /calendario continua coberta pelo routeRule ssr:false, mas /calendario/config não — a regra é exata, sem wildcard. Pelo próprio comentário do config, rota de painel fora da lista roda SSR e o bootstrap de auth no servidor é frágil: hard reload em /calendario/config pode deslogar/estourar.

Evidência: web/nuxt.config.ts:34 ('/calendario': { ssr: false }, sem /**) + existência de web/app/pages/calendario/config.vue na working tree; compare com '/cardapio' que tem as duas formas (linha exata + /**).

Ação recomendada: trocar por '/calendario/**': { ssr: false } (mantendo a entrada exata, como no padrão do cardápio) antes de commitar a página nova.

FE-04Sem manualChunks nem análise de bundleP2Esforço: SImpacto: baixo›

Problema: o split de bundle usa apenas o default por rota do Vite; nunca se mediu o tamanho do vendor nem se libs pesadas (TipTap, ApexCharts) vazam para o chunk inicial. Num SPA em que o primeiro paint depende do download do shell, isso é voo cego — pode estar ótimo ou péssimo, não há medição ("não medido").

Evidência: ausência de manualChunks em web/nuxt.config.ts; lazy loading real limitado a 5 componentes via web/app/utils/lazy-component.ts.

Ação recomendada: rodar uma análise de bundle (ex.: nuxt analyze / rollup-plugin-visualizer) quando o build for aprovado pelo usuário (regra do projeto: sem npm/build sem aprovação) e só então decidir se manualChunks vale a pena.
