Visão geral

Toda a produção do Omni roda em uma única VPS (85.31.62.33, Ubuntu 24.04 LTS, ~7,8GB de RAM medidos em 03/07), compartilhada com stacks de outros projetos. O build nunca acontece na VPS: as imagens saem do GitHub Actions para o GHCR e a máquina só faz pull. Essa disciplina de pipeline convivia com uma operação quase sem rede de proteção: zero monitoração, backup só no deploy e nenhum limite de memória nos containers.

✅ Atualização 03/07: com acesso à VPS, dois furos já foram tapados — backup diário agendado (cron 06:40, retenção 7/4, testado: dump de 177 MB) e monitoração de host (cron a cada 5 min: disco, RAM, load, containers unhealthy/restarting, healthz). As órfãs já estavam paradas (o pico de CPU foi histórico) e a RAM real é 7,8 GB. Ainda pendente (próximo deploy): mem_limits + healthchecks no compose (AC-11) e o /healthz com ping de banco + rotação de logs (AC-16).

Veredito: o pipeline de build/deploy é maduro para o tamanho do projeto — testes reais como gate do build, imagens imutáveis por SHA, deploy por pull com backup e smoke test. O que preocupa não é o caminho até a produção, e sim a produção em si: uma VPS única dividida com uma stack alheia (cujo Caddy roteia o painel), containers órfãos em crash-loop, nenhum limite de memória e nenhuma monitoração — hoje quem descobre que caiu é o usuário.

Pontos fortes confirmados

  • Build fora da VPS — build-images.yml compila e publica no GHCR; a VPS só faz pull + up --no-build. Elimina o risco de OOM de build em máquina pequena.
  • Testes como gate — migrations aplicadas em Postgres 16 real, go test ./..., vitest, npm audit (raiz bloqueante) e govulncheck rodam ANTES de qualquer imagem existir.
  • Nada exposto direto — em prod, todos os serviços publicam porta apenas em 127.0.0.1; a entrada é só pelo reverse proxy.
  • Imagens imutáveis por SHA — tag sha-<40hex>; o byte testado em staging é o promovido para prod.
  • Deploy com trilha de auditoria — workflow manual com inputs explícitos (ambiente, tag, backup, recreate) e resumo publicado por execução.

Fraquezas principais

  • AC-02 — stacks órfãs na VPS em crash-loop já consumiram 158% de CPU do dockerd (ver também 07-design-geral e 09-vps).
  • AC-16 — sem métricas, sem alertas, sem uptime monitor, sem agregação de logs: só /healthz + smoke no deploy (ver 07, 09).
  • AC-11 — nenhum serviço tem limite de memória; healthcheck só em postgres e api (ver 09-vps).
  • AC-05 — backup do banco só on-demand no deploy; sem cron nem cópia off-site (ver 03-banco-de-dados, 07, 09).
  • Acoplamento com stack alheia: a rede proxy de prod é a omnichannel-mvp_default de outro projeto.

CI/CD & deploy

Dois workflows com papéis limpos: build-images.yml testa e publica; deploy-vps.yml promove. A VPS nunca compila nada — regra escrita em comentário no próprio workflow e respeitada pelos métodos recomendados.

build-images.yml — o gate que vale a pena destacar

Dispara em push para main e refactor/multitenant-complete (ou manual). O job build só roda com needs: [test] verde — nenhuma imagem nasce sem passar pelos gates abaixo, na ordem:

1
Migrations reais — TestAllMigrationsApply contra um service container Postgres 16 de verdade (não mock). Pega migration quebrada antes de ela chegar perto da VPS.
2
Front — npm ci + nuxt prepare + suíte vitest (npm run test).
3
Auditoria de dependências — npm audit da raiz é bloqueante em high; o do web/ é warning-only (baseline conhecido, com aviso explícito no log até as deps do front serem atualizadas).
4
Back — go test ./... completo + go list -m -u (visibilidade de updates) + govulncheck (vulnerabilidades conhecidas no grafo Go).
5
Build + push — Buildx com cache do GHA por escopo (api/web), tags sha-<40hex> (imutável) + branch sanitizada, labels OCI apontando pro repo. Concurrency cancela build antigo da mesma ref.

Esse conjunto — migration test com banco real, govulncheck e audit bloqueante — é um ponto forte real, incomum em projeto deste porte. A ressalva fica para a cobertura que alimenta o gate: o front tem só 17 arquivos de teste para 313 componentes (AC-15, tratado em 02-frontend), então o gate do vitest cobre pouco do que poderia.

deploy-vps.yml — promoção manual e auditável

  • Só workflow_dispatch — nada vai para produção sem ação humana. Inputs: environment (staging/prod), image_tag (vazio = SHA do HEAD do ref), git_ref, backup_database (default true), force_recreate, skip_smoke_tests.
  • Backup opcional antes do deploy — pg_dump | gzip via SSH para backups/ na VPS. É a única forma de backup existente (AC-05: sem cron, sem off-site).
  • Pull + up --no-build — copia o compose por scp, grava IMAGE_TAG no .env remoto, puxa só api+web e sobe sem build. Migrations rodam no boot da imagem da api.
  • Smoke test — curl em / e /healthz do domínio público; deploy falha se qualquer um não devolver 200. Simples e suficiente como primeiro guarda-corpo.
  • Staging existe no workflow (path lista-atendimento-staging + .env.staging) mas não há rito documentado de usá-lo antes de release (IN-03).

Imagens (Dockerfiles)

  • api — multi-stage: builder Go → runtime bookworm-slim. O CMD encadeia migrate up && migrate bootstrap-erp-store && api: o schema sobe junto com o binário, sem passo manual.
  • web — multi-stage Node 24; o stage de build usa NODE_OPTIONS=--max-old-space-size=4096 (web/Dockerfile:13) por causa do OOM histórico do build Nuxt — mais um motivo para o build viver no CI, não na VPS.
  • Migração automática no boot significa que todo deploy que toca schema precisa do backup_database=true — o default true do workflow protege, mas os scripts npm dependem de disciplina.

Riscos operacionais

Nenhum destes riscos é teórico: a VPS já registrou crash-loop com 158% de CPU do dockerd, e um estouro de memória do waha ou do n8n hoje derrubaria o painel junto — sem que nenhum alerta disparasse.

P0  AC-02 — Stacks órfãs em crash-loop na mesma VPS ver também 07-design-geral · 09-vps

A stack omnichannel-mvp em /opt/omnichannel mantém 2 containers em crash-loop (postgres morto) que já consumiram 158% de CPU do dockerd na auditoria; as stacks omni-crow e omni-staging também estão órfãs na máquina. CPU e RAM queimadas são roubadas diretamente do orçamento de ~6GB do Omni.

⚠ Atenção crítica: o Caddy dessa mesma stack alheia é quem roteia o painel (omni.crowvisuals.com.br). Remover a stack inteira derruba a produção do Omni. A ação é cirúrgica: parar/remover apenas os containers quebrados, nunca o Caddy. Achado advisory — executar manualmente na VPS.

P1  AC-11 — Sem limites de memória; healthchecks incompletos ver também 09-vps

  • mem_limit/deploy.resources: 0 ocorrências nos dois compose. Qualquer container pode consumir a VPS inteira até o OOM killer do kernel escolher a vítima — que pode ser o postgres.
  • O waha (engine de WhatsApp) é o candidato clássico a comer memória sem teto; n8n vem logo atrás.
  • Healthcheck só em postgres e api: web, redis, waha e n8n podem estar mortos-vivos (processo up, serviço quebrado) sem que o Docker perceba ou reinicie.

P1  AC-16 — Zero monitoração de produção ver também 07-design-geral · 09-vps

  • Hoje existe: logs slog no stdout (via docker logs), /healthz e o smoke test do deploy. Só.
  • Não existe: métricas (Prometheus/Grafana), alertas, uptime monitor externo, agregação de logs. Se o painel cair às 3h, ninguém sabe até um cliente reclamar.
  • O crash-loop do AC-02 é a prova: consumiu CPU por tempo indeterminado sem nenhum alarme — foi descoberto por auditoria manual.

P1  AC-05 — Backup só on-demand, sem off-site ver também 03-banco · 07 · 09

  • Backup existe apenas acoplado a deploy: deploy-ship.ps1:87, deploy-vps-incremental.ps1:204-217 e o input backup_database do deploy-vps.yml:131-145.
  • Nenhum cron/timer no repo; semanas sem deploy = semanas sem backup.
  • Dumps ficam em /home/deploy/lista-atendimento/backups/ — no mesmo disco do banco. Falha da VPS leva dado e backup juntos.

P2  Acoplamento à rede omnichannel-mvp_default (IN-01)

  • A rede proxy de prod é externa e pertence a outra stack (docker-compose.prod.yml:250-254). Se alguém fizer docker compose down na stack omnichannel-mvp, a rede some e o compose do Omni deixa de subir.
  • O nome já é parametrizado (${PROXY_NETWORK_NAME}) — a migração para uma rede + Caddy próprios é factível sem tocar código, só infra.
  • Enquanto o acoplamento existir, vale a regra operacional já registrada: nunca parar o Caddy da stack alheia.

Orçamento de memória da VPS (estimativa declarada)

Perfis típicos de consumo — não medidos nesta sessão: postgres 512MB–1GB · api Go 100–300MB · web Node 300–500MB · caddy ~50MB · redis 50–150MB · waha 300MB–1GB · n8n 300–500MB · overhead Docker+SO ~600MB–1GB. Soma com automação plena: ~2,2–5,5GB numa VPS de ~6GB dividida com stacks alheias — funciona no cenário bom, mas sem folga para pico do waha nem para os órfãos do AC-02. O passo 0 de custo zero (remover órfãos + configurar limites) resolve a margem antes de qualquer upgrade de máquina; cenários de dimensionamento estão em 09-vps.

Oportunidades de melhoria

Backlog priorizado da área. P0 = agir já · P1 = próximas semanas · P2 = quando escalar. AC-* são achados canônicos da série; IN-* são locais desta página.

AC-02Stacks órfãs na VPS em crash-loop consumindo CPU/RAMP0Esforço: SImpacto: alto›

Problema: a stack omnichannel-mvp mantém 2 containers em crash-loop (postgres morto) que já consumiram 158% de CPU do dockerd; omni-crow e omni-staging também estão órfãs na mesma máquina de ~6GB que roda a produção do Omni.

Evidência: auditoria anterior na VPS (/opt/omnichannel); registrada em memória de projeto. Atenção: o Caddy dessa stack roteia o painel — nunca parar o Caddy, só os containers quebrados.

Ação recomendada: parar/remover os containers órfãos (advisory — executar manualmente na VPS, com o Caddy preservado). Ver também 07-design-geral e 09-vps.

AC-11Compose sem limites de memória e healthchecks faltando (web, redis, waha, n8n)P1Esforço: SImpacto: alto›

Problema: nenhum serviço tem teto de memória — o waha pode consumir a VPS inteira e o OOM killer do kernel decide quem morre (podendo ser o postgres). Sem healthcheck, web/redis/waha/n8n mortos-vivos passam despercebidos pelo Docker.

Evidência: grep mem_limit|deploy.resources = 0 matches em docker-compose.yml e docker-compose.prod.yml; healthcheck presente só em postgres e api (docker-compose.prod.yml:13-22,116-125).

Ação recomendada: definir mem_limit por serviço (waha e n8n primeiro), adicionar healthchecks e revisar restart policies. Ver também 09-vps.

AC-16Sem monitoração de produção (métricas, alertas, uptime, agregação de logs)P1Esforço: MImpacto: alto›

Problema: a única visibilidade de produção é healthz + smoke no momento do deploy e docker logs sob demanda. Queda fora do horário de deploy só é descoberta por reclamação de usuário; incidentes como o crash-loop do AC-02 correm por tempo indeterminado.

Evidência: nenhuma métrica exportada em nenhum serviço; sem Prometheus/Grafana, sem alertas, sem uptime monitor (levantamento de observabilidade desta série, 2026-07-02).

Ação recomendada: mínimo viável em camadas — (1) uptime monitor externo no domínio público, (2) node_exporter/cAdvisor na VPS, (3) alerta de disco/RAM/crash-loop. Ver também 07-design-geral e 09-vps.

AC-05Backup de banco só on-demand no deploy; sem agendamento nem off-siteP1Esforço: SImpacto: alto›

Problema: o pg_dump só roda quando alguém faz deploy com backup habilitado; período sem release = período sem backup. Os dumps ficam no mesmo disco do banco — falha catastrófica da VPS perde dado e backup de uma vez.

Evidência: deploy-ship.ps1:87, deploy-vps.yml:131-145, docs/DEPLOY_VPS.md:252; nenhum cron/timer no repo.

Ação recomendada: cron diário de pg_dump com retenção + cópia off-site (storage S3-like) + teste periódico de restore. Ver também 03-banco-de-dados, 07 e 09.

IN-01Rede proxy própria + Caddy próprio — desacoplar da stack omnichannel-mvpP2Esforço: MImpacto: médio›

Problema: a entrada de tráfego da produção do Omni depende de uma rede Docker e de um Caddy que pertencem a outra stack (omnichannel-mvp_default). Um docker compose down na stack alheia remove a rede e quebra o boot do Omni; qualquer mudança de Caddyfile de lá afeta o painel de cá.

Evidência: docker-compose.prod.yml:250-254 — proxy: external: true, name: ${PROXY_NETWORK_NAME:-omnichannel-mvp_default}; regra operacional "nunca parar esse Caddy" registrada em memória de projeto.

Ação recomendada: criar rede omni_proxy própria + serviço Caddy próprio no compose do Omni, migrar o roteamento de omni.crowvisuals.com.br em janela controlada e só então aposentar a dependência. O nome parametrizado torna a troca só-infra, sem mudança de código.

IN-02Healthcheck no serviço webP2Esforço: SImpacto: médio›

Problema: o web (Nuxt/Nitro) é o único serviço sempre-ativo voltado ao usuário sem healthcheck — se o Node travar com o processo vivo, o Docker considera o container saudável e não reinicia; o Caddy segue roteando para um serviço morto.

Evidência: docker-compose.prod.yml:132-160 — bloco do web sem healthcheck:, enquanto api (linhas 116-125) e postgres (13-22) têm. A api inclusive usa depends_on: condition: service_healthy do postgres — o padrão já existe no arquivo.

Ação recomendada: healthcheck HTTP simples na porta 3003 (mesmo padrão do da api) + o Caddy passa a ter um upstream confiável. Subconjunto rápido do AC-11 — vale fazer junto.

IN-03Staging sob demanda já existe — falta rito de uso antes de releaseP2Esforço: SImpacto: médio›

Problema: a infra de staging está pronta (path lista-atendimento-staging, .env.staging, input environment no workflow, mesma imagem por SHA), mas não há rito documentado de passar por ela antes de promover para prod — o benefício de "mesmo byte testado" só se realiza se staging for de fato usado.

Evidência: deploy-vps.yml:79-82 resolve staging como default do workflow; plano em docs/deploy/REGISTRY_STAGING_DEPLOY_PLAN.md descreve staging same-VPS sob demanda.

Ação recomendada: documentar checklist curto no doc de deploy: releases que tocam schema ou fluxo crítico sobem primeiro em staging (mesmo IMAGE_TAG), smoke manual, depois promoção para prod com a mesma tag.
