Visão geral

Estado da segurança do Omni na fotografia local de 2026-07-02: o que a aplicação garante hoje (autenticação, autorização, superfície exposta, segredos) e onde estão os riscos residuais reais — que são operacionais, não de código.

Veredito: a fundação de segurança está acima da média para o estágio do produto: parametrização total de SQL, headers completos em todas as respostas, guard de secret no boot de produção (com teste), e sessões revogáveis de verdade — logout derruba o token no servidor, coisa rara em MVP. Os riscos residuais não estão no código de aplicação, e sim na operação: o app conecta no Postgres como superuser (AC-04), há um dump real de banco e tokens de teste em tmp/ no disco de dev (AC-03), e o isolamento multi-tenant depende 100% da disciplina de WHERE na aplicação, sem rede de segurança no banco.

Camadas de defesa hoje

1
Borda HTTP — CORS whitelist, rate limit por identidade, headers de segurança, body limitado a 1MB com DisallowUnknownFields
2
Autenticação — JWT HMAC-SHA256 com claim sid + sessão persistida em core.user_sessions (revogação real)
3
Autorização — RBAC dinâmico por account (roles clonados de templates + overrides por usuário) + guards de módulo + X-Account-Id
4
Store — todo acesso a dado passa por WHERE tenant_id/account_id nas stores, com queries 100% parametrizadas
5
Banco (ausente) — sem RLS e app conectando como superuser: se as camadas 3–4 falharem, o banco não segura nada (AC-04, ver 03-banco-de-dados)

AuthN & AuthZ

Autenticação com sessão server-side revogável (não é JWT stateless puro) e autorização em dois estágios: RBAC dinâmico no back + gating fail-closed no front.

Fluxo de autenticação

Loginsenha validada com bcrypt cost 10 (default; mínimo de produção validado no boot)
→
JWT HMAC-SHA256assinado com AUTH_TOKEN_SECRET, carrega claim sid (id da sessão)
→
core.user_sessionssessão persistida no banco; Authenticate checa IsRevoked a cada request
→
Logoutrevoga a sessão no servidor → próximo request com o mesmo token = 401
Sem refresh token (AC-10)TTL ~12h via AUTH_TOKEN_TTL; front redireciona pro login no 401 e proativamente no expiresAt (auth-bridge). Sessão longa é o trade-off atual.

Ponto forte raro em MVP: revogação real

A maioria dos MVPs usa JWT stateless — logout só apaga o cookie e o token continua válido até expirar. Aqui não: o claim sid amarra o token a uma linha em core.user_sessions, e o middleware consulta a revogação a cada request. Logout derruba a sessão de verdade, e um token vazado pode ser morto server-side.

O custo é uma consulta ao banco por request — o cache que resolveria isso existe mas está desligado (AC-01, tratado como performance em 01-backend e 05-performance; do ponto de vista de segurança, o estado atual é o mais rigoroso possível).

Autorização — RBAC em dois estágios

  • Back (autoridade): roles do core clonados de templates por account + overrides por usuário; papéis coarse do legado (fila) mapeados para o modelo novo
  • Escopo por header: X-Account-Id obrigatório nas rotas multi-tenant, validado por guards antes do handler
  • Front (fail-closed): domain/utils/permissions.ts (916 linhas) gateia 28 workspaces por view/editPermission — sem permissão, a seção não renderiza
  • Ressalva conhecida: has() retorna false pro platform_admin; todo gating precisa do padrão isPlatformAdmin || has(...) — um esquecimento esconde UI do admin (é usabilidade, não vazamento)

Checklist de controles

  • SQL 100% parametrizado — placeholders $1,$2 em todas as stores; nenhuma concatenação de query encontrada no back
  • Validação de input — ReadJSON com DisallowUnknownFields + io.LimitReader de 1MB em todo body; campo desconhecido = 400 (mass assignment bloqueado por design)
  • Headers de segurança — httpapi/security_headers.go: nosniff, X-Frame-Options DENY, Referrer-Policy strict, COOP same-origin, CSP default-src 'none'; frame-ancestors 'none', HSTS quando HTTPS
  • Sessões revogáveis — logout → 401 imediato; token vazado pode ser revogado server-side
  • CORS whitelist + WS CheckOrigin — origens configuradas por env; o WebSocket valida a mesma whitelist no handshake (não aceita origem qualquer)
  • Rate limit — token bucket 60 req/min por identidade (user/token/IP) com bucket extra por X-Account-Id, 429 + Retry-After; mas é em memória por instância — numa 2ª instância o teto efetivo dobra (AC-08, ver 05-performance)
  • RLS ausente — decisão de design de 2026-06-29 (app é superuser + public.* são views); isolamento é 100% aplicativo — detalhado na aba Superfície e em 03-banco-de-dados
  • Refresh token ausente — access token de ~12h sem rotação (AC-10); aceitável hoje, encurtar quando houver refresh

Superfície & dados

Das ~377 rotas HTTP, só um punhado é público — o resto exige token. O ponto nevrálgico não é a superfície externa, é o isolamento entre tenants por dentro.

A única escrita pública é o pedido do cardápio — exatamente a rota com validação mais estrita (campo desconhecido derruba com 400, episódio já vivido e corrigido no caso do customer.address).

Isolamento multi-tenant — como funciona e onde pode quebrar

Request autenticadotoken + X-Account-Id
→
GuardsRequireAuth + validação de acesso à account/módulo
→
StoreWHERE tenant_id/account_id em toda query
→
Bancosem RLS — se um WHERE for esquecido, o banco entrega dado de outro tenant
  • O que garante hoje: guards de escopo + filtro por account em todas as stores; um bug de WHERE é a única forma de vazamento entre tenants
  • Mitigação estrutural: o padrão de adapter de escopo (platform/app/operations_store_scope_adapter.go) resolve o tenant pela loja para rotas de operação (platform_admin tem TenantID vazio), + code review com essa lente
  • Rede de segurança ausente: RLS foi tentado e removido por design (2026-06-29) — o app conecta como omni=SUPERUSER e public.* virou view; RLS em view não funciona. Replano em docs/RLS_PLAN.md exige role não-superuser primeiro — AC-04, ver também 03-banco-de-dados e 07-design-geral

Uploads e arquivos

  • Uploads servidos de volume próprio (UPLOADS_DIR), fora do bundle da aplicação
  • CSP da API é default-src 'none' — um HTML malicioso servido como upload não carrega recurso nem executa em iframe (frame-ancestors 'none')
  • nosniff impede o browser de "adivinhar" content-type de upload como script

PII — dados de pessoa física no sistema

  • Clientes finais do cardápio: nome, endereço e telefone entram pela rota pública de pedido e ficam no banco do tenant
  • Usuários do painel: e-mail e hash de senha (bcrypt) em core.users
  • Gap formal: não há inventário de dados pessoais nem política de retenção/eliminação documentada — obrigação LGPD que vira relevante com clientes reais de cardápio. Tratado como SEC-03 (P2) na aba Oportunidades
💡 O dump de 245,35MB em tmp/ (aba Segredos, AC-03) também é superfície de dados: é um banco real pré-rename parado em disco de dev — do ponto de vista LGPD, dado pessoal fora do ambiente controlado.

Segredos & config

Nenhum segredo hardcoded além do default de dev — e o boot de produção recusa esse default. O problema de segredos do Omni está no disco local, não no repositório.

Guard do secret de dev — existe e tem teste (AC-09)

O briefing inicial da série dizia "sem guard"; a medição desmentiu. Validate() em platform/config/config.go:193-208 roda quando APP_ENV=production e aborta o boot se AUTH_TOKEN_SECRET ainda for o default dev-secret-change-me (config.go:12) ou se AUTH_BCRYPT_COST estiver abaixo do mínimo de produção (10). Coberto por teste em config_test.go:75-82.

  • Secret default em produção = processo nem sobe — classe inteira de incidente eliminada
  • bcrypt fraco em produção = mesmo tratamento
  • Ressalva: a comparação é com a string exata production (case-insensitive). APP_ENV=prod ou staging passam sem validação nenhuma — fail-open para grafias não previstas. Correção é inverter: validar sempre que Env != development/test

Segredos em disco local (AC-03)

tmp/ soma 254,18MB, tudo gitignored (.gitignore:42) — nada disso vaza pelo git. Mas o disco da máquina de dev é superfície:

  • pg_dump real de 245,35MB — tmp/omni-rename-20260521_200120/lista-da-vez-before-omni.dump, banco completo pré-rename de 2026-05-21, com dados reais
  • Tokens e chave de teste: token.txt, runtime_token*.txt, full_token.txt, secret.key — credenciais em texto plano no disco
  • Ação é advisory: confirmar que o dump pré-rename não é mais necessário antes de excluir (dados reais — nunca automatizar). Ver também relatório 08

Higiene de env vars — boa

  • Templates separados por ambiente na raiz: .env.docker.example, .env.staging.example, .env.production.example — o operador sabe exatamente o que preencher
  • Nenhuma credencial hardcoded no código além do default de dev explícito e barrado no boot de produção
  • Config centralizada em platform/config/config.go com defaults documentados (TTLs, CORS, SMTP, pool, bcrypt)
  • Defaults de conveniência de dev existem (ex.: senha padrão de consultor via AUTH_CONSULTANT_DEFAULT_PASSWORD) — sobrescrever em produção é responsabilidade do env, não há guard específico para eles

Gaps operacionais de segredo

  • Rotação do AUTH_TOKEN_SECRET sem runbook (SEC-01): trocar o secret invalida todos os JWTs de uma vez (comportamento aceitável e até desejável em incidente) — mas o procedimento e o efeito não estão documentados; num vazamento, improvisar custa tempo
  • npm audit do web é warning-only no CI (SEC-02): o audit da raiz bloqueia em high, o do web só avisa — vulnerabilidade high em dependência do front passa sem quebrar a pipeline; falta decidir a política (bloquear high? allowlist?)
  • Na direção certa: o CI já roda govulncheck (Go) e npm audit raiz como gate do build de imagem — ver 04
💡 Contexto do AC-09: a prioridade é P2 (não P0) justamente porque o guard existe, funciona e tem teste — o risco residual é só a grafia do env. Não recriar esse achado com prioridade maior em outras páginas; ele também aparece em 01-backend.

Oportunidades de melhoria

Backlog priorizado da área. P0 = agir já · P1 = próximas semanas · P2 = quando escalar. Itens AC-* são canônicos da série (mesmo id/prioridade em todas as páginas); SEC-* são achados locais desta página.

AC-03tmp/ local com dump real de banco (245MB) e tokens/secret.key em discoP0Esforço: SImpacto: médio›

Problema: o diretório tmp/ da máquina de dev guarda um pg_dump completo do banco real pré-rename (dados de produção da época) e credenciais em texto plano (token.txt, runtime_token*.txt, secret.key). Está fora do git, mas qualquer comprometimento ou perda da máquina de dev expõe banco inteiro + tokens.

Evidência: tmp/omni-rename-20260521_200120/lista-da-vez-before-omni.dump — 245,35MB de 254,18MB totais do tmp/; gitignored em .gitignore:42.

Ação recomendada: advisory — confirmar que o dump pré-rename não é mais necessário e excluir; revogar/regenerar os tokens salvos e apagar os .txt. Nunca automatizar sem confirmação (dados reais). Ver também relatório 08.

AC-04App conecta no Postgres como superuserP1Esforço: MImpacto: alto›

Problema: o runtime usa a role omni que é SUPERUSER — uma SQL injection (hoje inexistente, mas é a hipótese que segurança assume) ou um bug de escopo teria poder total sobre o cluster, incluindo DDL e leitura cross-tenant. Também é o bloqueio formal para reintroduzir RLS como rede de segurança.

Evidência: decisão de RLS de 2026-06-29 (removido por design: omni=SUPERUSER + public.* são views); docs/RLS_PLAN.md exige role dedicada antes de qualquer RLS.

Ação recomendada: criar role least-privilege (sem DDL) para o runtime; superuser fica só no migrate. É o pré-requisito do replano de RLS. Ver também 03-banco-de-dados e 07-design-geral.

AC-09Guard do dev secret só dispara com APP_ENV exatamente 'production'P2Esforço: SImpacto: médio›

Problema: o guard de boot existe, funciona e tem teste — mas é fail-open para grafias não previstas: APP_ENV=prod ou staging sobem com AUTH_TOKEN_SECRET default e bcrypt fraco sem reclamar.

Evidência: back/internal/platform/config/config.go:193-208 (comparação EqualFold com "production"); teste em config_test.go:75-82.

Ação recomendada: inverter a lógica para fail-closed — validar sempre que Env != development/test. Uma linha de mudança + ajustar o teste. Ver também 01-backend.

AC-10Sem refresh token (sessão de 12h, logout só server-side)P2Esforço: MImpacto: médio›

Problema: o access token vale ~12h sem rotação. Um token vazado é utilizável até expirar ou até alguém revogar a sessão manualmente. A janela é longa demais para o padrão de mercado (access curto + refresh rotativo), e encurtar o TTL hoje pioraria a UX (relogin no meio do expediente).

Evidência: auth/tokens.go; AUTH_TOKEN_TTL default de 12h (platform/config/config.go:166); front faz redirect proativo no expiresAt (auth-bridge).

Ação recomendada: implementar refresh token rotativo e encurtar o TTL do access. A infra de sessão revogável em core.user_sessions já é metade do caminho.

SEC-01Rotação do AUTH_TOKEN_SECRET sem runbookP2Esforço: SImpacto: médio›

Problema: não existe procedimento documentado para trocar o AUTH_TOKEN_SECRET em produção. A troca invalida todos os JWTs de uma vez (todo mundo desloga) — efeito aceitável e até desejável num incidente de vazamento, mas quem operar sob pressão precisa saber a ordem exata (trocar env → recriar api → comunicar relogin) sem improvisar.

Evidência: AUTH_TOKEN_SECRET lido em platform/config/config.go:165; nenhum runbook de rotação nos 107 docs de docs/.

Ação recomendada: escrever runbook curto de rotação (passos, efeito colateral, verificação) junto das Notas de Deploy do doc canônico; ensaiar uma vez em staging.

SEC-02npm audit do web é warning-only no CI — política indefinidaP2Esforço: SImpacto: médio›

Problema: no gate de build do CI, o npm audit da raiz bloqueia em severidade high, mas o do web/ só emite warning. Uma vulnerabilidade high numa dependência do front (a maior árvore de deps do projeto) passa para a imagem publicada sem quebrar nada — e warning que ninguém lê é warning que não existe.

Evidência: .github/workflows/build-images.yml — job test: npm audit raiz (high bloqueante) vs npm audit web (warning), conforme levantamento do CI.

Ação recomendada: decidir a política: ou bloquear high no web também (com allowlist para falsos positivos de dev-deps), ou registrar formalmente por que é só warning e revisar o output a cada release.

SEC-03Inventário LGPD dos dados de cliente final inexistenteP2Esforço: MImpacto: médio›

Problema: o cardápio público coleta nome, endereço e telefone de consumidores finais (pessoas físicas que nem são clientes do Omni — são clientes dos tenants). Não há inventário de onde esse dado vive, por quanto tempo fica, nem procedimento de eliminação a pedido do titular. Com tenants reais operando (caso Mostarda em produção), isso é obrigação legal, não polimento.

Evidência: rota pública /v1/public/cardapio/{slug}/orders aceita customer com nome/endereço/telefone; nenhum doc de retenção/eliminação nos 107 .md de docs/.

Ação recomendada: mapear tabelas com PII (pedidos do cardápio, core.users, CRM), definir prazo de retenção por categoria, e implementar rotina de anonimização/eliminação + registro do procedimento em doc.
