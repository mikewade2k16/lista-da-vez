O que estamos construindo

Esta é a página-âncora da série: ela responde à pergunta "estamos construindo, desde o início, a melhor aplicação para escalar e ser usada por muitas pessoas?" — cruzando os achados dos relatórios 01 a 06 numa visão única de produto e arquitetura.

Resposta curta: sim, com ressalvas. A fundação — monorepo com backend modular, multi-tenant no core do modelo de dados, SPA + API stateless, CI que testa migrações de verdade e documentação incomum para este estágio — é a arquitetura certa para virar algo grande. O que precisa de correção não é retrabalho estrutural: é dívida pontual (cache de auth desligado, listagens sem paginação) e higiene operacional (VPS compartilhada, backup sem agendamento, zero monitoração). O detalhe da resposta está na aba "Caminho de escala".

O produto em um parágrafo

O Omni é um painel SaaS multi-tenant de gestão para agências e suas lojas/clientes: operação de fila de atendimento em tempo real (WebSocket), CRM/ERP com BI (integração Pérola via FTP), tasks em kanban, cardápio digital e bio públicos servidos por fronts separados, calendário editorial com IA, automação de WhatsApp (n8n + WAHA + Claude) e assistente de Meta Ads. Uma agência (organization) agrupa contas (accounts); cada conta liga módulos, papéis clonados de templates e usuários com overrides — o RBAC é dinâmico e resolvido no banco, não hardcoded.

A leitura importante: tudo converge para uma única API Go stateless. Fronts públicos e automação não têm caminho paralelo para o banco — o isolamento multi-tenant e as regras de negócio vivem num lugar só. Isso é o que torna o desenho escalável horizontalmente (ver aba "Caminho de escala") e auditável.

Decisões estruturais que são a base certa

  • Monorepo — back, web, automação, deploy e docs versionados juntos; uma mudança de contrato API↔front vive num diff só.
  • Backend modular padronizado — 20 módulos com o mesmo esqueleto (module.go/http.go/service.go/store_postgres.go) e um AGENT.md por módulo (31 no back). Custo de entender/mexer num módulo novo é baixo e previsível.
  • Trilha única de migrations — migrator próprio, transacional, com tracking em schema_migrations; o schema evolui num caminho só, sem drift entre ambientes.
  • Multi-tenant no core do modelo — core.accounts/organizations/account_users, papéis clonados de templates por conta, overrides por usuário, header X-Account-Id. Não é multi-tenant "colado depois": é o eixo do dado.
  • SPA + API stateless — sessão no banco (revogável), token no cliente, nenhum estado de request no servidor; é o pré-requisito nº 1 para rodar N instâncias.
  • CI com teste real de migração — build-images.yml sobe Postgres 16 e roda TestAllMigrationsApply + go test + vitest + govulncheck como gate do build de imagem. Migração quebrada não vira imagem.

Trade-offs conscientes (e por que são aceitáveis)

  • RLS adiada por design — o app conecta como superuser e public.* são views, então RLS no Postgres seria no-op; o isolamento é 100% aplicativo (WHERE tenant/account). Decisão documentada (2026-06-29, docs/RLS_PLAN.md) com pré-requisito claro: role não-superuser primeiro (AC-04, ver 03 e 06).
  • BFF eliminado — ADR 0002 matou a camada Nitro intermediária; o front fala direto com a API Go. Menos um hop, menos um lugar para lógica vazar. Resíduo: o mock de finance ainda vive em web/server/ (10 arquivos — AC-12, ver 02).
  • Sem microserviços — um binário Go com módulos internos é a escolha correta para o estágio: deploy de uma imagem, transações locais, zero rede interna. A modularidade já dá as costuras se um dia for preciso extrair algo.
  • Caches em memória local — goal progress (120s), module guard (60s), rate limit — funcionam bem em 1 instância; viram pré-requisito de Redis apenas no cenário multi-instância (AC-08).

Capacidade estimada

Quantas pessoas o Omni aguenta hoje, do jeito que está? Resposta honesta com a conta aberta — e com as premissas explícitas antes de qualquer número.

⚠️ Premissas — leia antes dos números. Isto é uma estimativa estática: nenhum load test foi executado (não há k6/baseline no repo). Os números de consumo por serviço são perfis típicos declarados como estimados no levantamento; os fatos de configuração (pool, rate limit, caches) são medidos no código. A faixa final é uma conta de engenharia, não uma medição — trate como ordem de grandeza até existir um teste de carga.

A conta de padeiro, passo a passo

1
O que um usuário ativo custa. O painel é SPA: depois do primeiro load (estático, barato de servir), um usuário ativo gera na ordem de 2–6 requests/min à API + 1 conexão WebSocket persistente (estimativa declarada; varia por tela — a Operação é mais falante que o CRM). O rate limit de 60 req/min por identidade confirma que o sistema foi dimensionado para esse perfil.
2
O que a API teoricamente entrega. Go stateless com pool de 10 conexões e queries típicas de milissegundos suporta, no papel, centenas de requests/segundo — ordens de magnitude acima do que dezenas de usuários geram. O gargalo não é o modelo de execução do Go.
3
O que corta a teoria na prática. (a) Toda request autenticada faz uma query extra de auth porque o PrincipalCache está desligado (AC-01) — o pool de 10 vira o funil sob pico; (b) endpoints de reports/analytics/BI carregam histórico completo ou até 5.000 registros num payload (AC-06) — um relatório aberto no fim do mês compete por RAM e conexões com a operação ao vivo; (c) a VPS de ~6GB é dividida com n8n/waha/redis e com stacks órfãs que já consumiram 158% de CPU do dockerd (AC-02), sem nenhum mem_limit isolando os vizinhos (AC-11).
4
Faixa honesta hoje. Dezenas a poucas centenas de usuários simultâneos ativos no painel sem degradar — o teto real vem da RAM/CPU compartilhada e dos payloads sem paginação, não do código Go. Para os fronts públicos (cardápio/bio), que são estáticos e consomem /v1/public/* com rate limit, milhares de visitantes são viáveis desde que haja cache na borda — o custo por visitante é muito menor que o de um operador logado.

Caminho de escala

Três estágios, do custo zero ao multi-instância. O ponto central: nenhum estágio exige reescrever o que existe — a arquitetura atual já deixou as costuras prontas; falta executar a lista de cada degrau.

1
Estágio 1 — A casa de hoje, arrumada (custo ~zero, dias de trabalho). Remover as stacks órfãs da VPS (AC-02), colocar mem_limit e healthchecks no compose (AC-11), ligar o PrincipalCache que já está implementado (AC-01) e agendar backup diário com cópia off-site (AC-05). Nada disso é feature — é tirar risco de mesa. Resultado: a mesma VPS passa a suportar o curto prazo com folga e sem sustos causados por terceiros.
2
Estágio 2 — Pronta pra crescer (semanas). Redis externo assumindo cache, rate limit e pub/sub do WebSocket (AC-08); role de banco não-superuser para o runtime (AC-04) — que também destrava o replano de RLS; monitoração mínima viável: uptime externo + métricas de host + alerta de disco/RAM/crash-loop (AC-16); e um baseline de carga com k6 para trocar a estimativa estática desta série por número medido. Resultado: centenas a milhares de usuários com margem conhecida.
3
Estágio 3 — Multi-instância (quando a demanda pedir). N réplicas da API atrás de load balancer (o stateless já permite), Postgres gerenciado com réplica de leitura, SPA servido por CDN/objeto estático. Pré-requisitos de software são exatamente os do estágio 2 — por isso a ordem importa. Resultado: dezenas de milhares de usuários sem mudança de arquitetura.

O que JÁ está pronto para escalar

  • API stateless — sessão no banco, zero estado de request no processo; replicar é subir container.
  • Modularidade — 20 módulos com fronteiras claras; se um domínio explodir de carga (ex.: queue, com 22.233 linhas), a costura para extraí-lo existe.
  • WS hub isolável — o hub in-memory está atrás de um módulo realtime próprio; trocar o transporte interno por pub/sub é mudança local, não espalhada.
  • CI por imagem — build no GitHub Actions → GHCR; a VPS só faz pull. Adicionar uma segunda máquina não muda o pipeline.
  • Fronts públicos desacoplados — TAVOLA e crow-nuxt são estáticos e falam só com /v1/public/*; escalam por CDN sem tocar no painel.

O que TRAVA a escala hoje

  • Caches e rate limit locais — em 2 instâncias, cada processo tem sua própria contagem e seu próprio cache (AC-08). É o único bloqueio técnico real do scale-out.
  • VPS única e compartilhada — não há segunda máquina, e a primeira divide RAM com vizinhos sem limites (AC-02/AC-11).
  • Superuser no runtime — além do risco, impede RLS como segunda camada de isolamento quando houver mais contas (AC-04).
  • Voar às cegas — sem métricas nem alertas (AC-16), qualquer degradação em escala será descoberta pelo cliente, não pelo dashboard.
  • Payloads sem paginação — não bloqueia replicar, mas multiplica o custo de cada instância (AC-06).
Veredito explícito — "estamos construindo desde o início a melhor aplicação para escalar e ser usada por muitas pessoas?"

Sim, com ressalvas — e as ressalvas têm nome e preço. A fundação está certa: backend modular e stateless, multi-tenant no coração do modelo de dados, trilha única de migrations, CI que bloqueia imagem em teste quebrado, e uma cultura de documentação (107 docs, ADRs, AGENT.md por módulo) que normalmente só aparece em times bem maiores. Nada do que foi encontrado nesta série exige retrabalho estrutural — não há "arquitetura errada" para desfazer. O que existe é dívida pontual e operacional, concentrada em cinco ações que destravam o resto:

AC-01 ligar o PrincipalCache (já implementado)  ·  AC-02 limpar as stacks órfãs da VPS  ·  AC-05 backup agendado + off-site  ·  AC-16 monitoração mínima viável  ·  AC-06 paginação nas listagens pesadas.

Feito isso, o Omni entra no estágio 2 com a consciência tranquila de quem construiu para durar.

Oportunidades de melhoria

Backlog consolidado da visão geral — os achados canônicos que definem o caminho de escala, com referência cruzada às páginas onde cada um foi analisado em profundidade. P0 = agir já · P1 = próximas semanas · P2 = quando escalar.

AC-01PrincipalCache implementado mas desligado — auth consulta o banco a cada requestP0Esforço: SImpacto: alto›

Problema: o cache de principal existe e está testado, mas não há nenhum wiring em produção — toda request autenticada paga uma consulta de revogação de sessão no banco, transformando o pool de 10 conexões no funil de qualquer pico.

Evidência: httpapi/principal_cache.go:24 + auth/AGENT.md:97; zero chamadas de SetPrincipalCache fora de testes em app.go.

Ação recomendada: ligar o cache com TTL curto + invalidação pelos eventos realtime já existentes (user.session.revoked, role.permissions.changed). Ver também 01-backend e 05-performance.

AC-02Stacks órfãs na VPS em crash-loop consumindo CPU/RAMP0Esforço: SImpacto: alto›

Problema: a mesma VPS de ~6GB que roda o Omni hospeda a stack omnichannel-mvp com 2 containers em crash-loop que já consumiram 158% de CPU do dockerd — o teto de capacidade do produto é definido por código que não é dele.

Evidência: auditoria anterior na VPS: omnichannel-mvp em /opt/omnichannel, 2 containers em crash-loop (postgres morto). Atenção: o Caddy dessa stack roteia o painel — nunca parar o Caddy, só os containers quebrados.

Ação recomendada: parar/remover os containers órfãos (advisory — executar manualmente na VPS, preservando o Caddy). Ver também 04-infra e 09.

AC-05Backup de banco só on-demand no deploy; sem agendamento nem off-siteP1Esforço: SImpacto: alto›

Problema: o pg_dump só acontece acoplado a deploy; se a VPS morrer numa semana sem deploy, perde-se a semana — e não há cópia fora da própria máquina.

Evidência: deploy-ship.ps1:87, deploy-vps.yml:131-145, docs/DEPLOY_VPS.md:252; nenhum cron/timer no repo.

Ação recomendada: cron diário de pg_dump + retenção + cópia off-site (objeto S3-like); testar restore periodicamente. Ver também 03-banco, 04-infra e 09.

AC-16Sem monitoração de produção (métricas, alertas, uptime, agregação de logs)P1Esforço: MImpacto: alto›

Problema: a única visibilidade de produção é healthz + smoke test no deploy + docker logs manual; degradação, disco cheio ou crash-loop serão descobertos pelo cliente, não por alerta. É a nota mais baixa do scorecard (3,0).

Evidência: nenhuma métrica exportada (sem Prometheus/Grafana), sem alertas, sem uptime monitor, sem agregação de logs — verificado no repo e nos workflows.

Ação recomendada: mínimo viável primeiro: uptime externo + node_exporter/cAdvisor + alerta de disco/RAM/crash-loop. Ver também 04-infra e 09.

AC-06Listagens sem paginação (reports, analytics, BI)P1Esforço: MImpacto: alto›

Problema: três famílias de endpoints carregam dados sem teto: reports sem LIMIT/OFFSET, analytics puxando o histórico completo da loja e BI devolvendo até 5.000 registros num payload único — o custo cresce com o tamanho do cliente, exatamente o oposto do que um SaaS multi-tenant quer.

Evidência: queue/reports/store_postgres.go:39-150 (sem LIMIT); queue/operations/store_postgres.go:565-617 (histórico completo); bi/service.go:23-24 (pageLimit=100 × maxPages=50).

Ação recomendada: LIMIT/OFFSET ou cursor + agregação no SQL; teto por página. Ver também 01-backend, 03-banco e 05-performance.

AC-07105 arquivos front acima de 450 linhas + components.css monolítico (4.480)P1Esforço: LImpacto: médio›

Problema: um sexto dos arquivos de código do front está acima do teto de 450 linhas dos princípios de engenharia; arquivos de 2.000–3.000 linhas concentram lógica que deveria estar distribuída, e o CSS monolítico dificulta saber o que é seguro mexer.

Evidência: medição wc -l 2026-07-02; top: useTasksPageContext.ts 3.029, roadmap-data.ts 2.614 (majoritariamente dado declarativo), MultiStoreGoalsSection.vue 2.334; components.css 4.480 linhas.

Ação recomendada: quebrar os >1.000 primeiro; fatiar components.css por domínio; regra no lint-staged. Ver também 02-frontend.

AC-04App conecta no Postgres como superuserP1Esforço: MImpacto: alto›

Problema: o runtime roda com o usuário omni = SUPERUSER — qualquer bug de SQL vira acesso total, e é o bloqueio explícito para RLS como segunda camada de isolamento multi-tenant.

Evidência: decisão RLS de 2026-06-29 (omni=SUPERUSER; docs/RLS_PLAN.md exige role dedicada antes de qualquer RLS).

Ação recomendada: criar role least-privilege (sem DDL) para o runtime; superuser só no migrate. Ver também 03-banco e 06-seguranca.

AC-08Caches e rate limit em memória local — travam scale-out horizontalP2Esforço: MImpacto: alto (na escala)›

Problema: goal progress (120s), module guard (60s) e os buckets do rate limit vivem dentro do processo; em 1 instância funcionam bem, mas na 2ª instância cada processo tem sua própria verdade — rate limit dobra na prática e caches divergem.

Evidência: caches todos in-process, sem Redis (verificado no back); é o único bloqueio técnico real do estágio multi-instância.

Ação recomendada: abstrair atrás de interface e mover para Redis quando for escalar — é pré-requisito do cenário Escala, não urgência de hoje. Ver também 01-backend, 05-performance e 09.

DG-01Definir SLO simples (latência p95 + uptime) quando houver métricasP2Esforço: SImpacto: médio›

Problema: "escalar sem degradar" não tem definição operacional no projeto — sem um alvo explícito de latência e disponibilidade, capacidade e prioridade de dívida viram opinião, e esta própria série teve que estimar em vez de medir.

Evidência: nenhuma métrica exportada hoje (AC-16) e nenhum documento de SLO/SLA em docs/; a estimativa de capacidade desta página é estática por falta de baseline.

Ação recomendada: depois do mínimo de monitoração (AC-16), fixar dois números simples — ex.: p95 de latência da API e uptime mensal alvo — e usar o baseline de k6 do estágio 2 para validar a faixa de capacidade estimada aqui. Achado local desta página.
