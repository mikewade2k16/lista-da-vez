Relatórios

Os 9 relatórios da série. Cada página tem tabs próprias e um backlog filtrável por P0/P1/P2. Bolinha: nota ≥ 7 · 5–6,9 · < 5.

01 · Backend

API monolítica em Go com 20 módulos plugáveis (~93,6 mil linhas, ~377 rotas), a peça mais madura do produto: padrão idêntico em todos os módulos, segurança de entrada acima da média e CI com testes como gate. As duas dívidas críticas foram pagas e estão em produção (PrincipalCache ~89% de hit; paginação com teto); resta o recorte de arquivos grandes.

1 P01 P15 P2 nota 8,5

02 · Frontend

Nuxt 4.4.2 100% SPA com 622 arquivos e 163.129 linhas em 4 layers; rico em features, com api-client enxuto (dedupe de GETs) e realtime WS. Avanços live: BFF mock removido (finance na API Go), components.css fatiado e onda 1 de testes (144 verdes). Trava principal: 105 arquivos acima de 450 linhas (AC-07, parcial).

0 P03 P14 P2 nota 7,0

03 · Banco de dados

Um PostgreSQL 16 único serve todos os domínios, e a migração longa do public.* legado para schemas por domínio foi bem executada (backfills incrementais, drift zero antes do drop). Os dois riscos operacionais foram pagos: api conecta como omni_app least-privilege (live em prod) e o backup é diário agendado com retenção. Faltam off-site (rclone) e drill de restore mensal.

0 P04 P13 P2 nota 8,0

04 · Infraestrutura

Pipeline de build/deploy maduro (CI com gate de testes reais, imagens GHCR, portas só em 127.0.0.1). Limites de memória, healthchecks, monitoração e backup agendado estão live desde 03/07. O que segura: VPS única compartilhada com stacks alheias e o runbook AC-04 manual (causou ~1h de 502 no deploy — prevenção ac-04b proposta).

1 P03 P13 P2 nota 7,5

05 · Performance

Go enxuto contra Postgres bem indexado (243 índices, pool pgx saudável, SPA estática), sem incêndio para o tamanho atual. Os dois maiores custos com crescimento foram pagos e estão live: PrincipalCache em prod com ~89% de hit e paginação com teto em reports/analytics/BI. Próximo salto honesto exige medição sob carga (load test + EXPLAIN), ainda não feita.

1 P03 P13 P2 nota 8,0

06 · Segurança

Fundação de código acima da média para o estágio: SQL 100% parametrizado, 6 headers de segurança em toda resposta, sessões revogáveis de verdade e guard de secret no boot de produção. Os dois maiores riscos operacionais foram eliminados: a api roda como omni_app least-privilege em produção e o tmp/ foi higienizado (dump + segredos removidos). Resta o isolamento multi-tenant só no WHERE da aplicação — RLS futuro, com o 1º pré-requisito destravado pelo AC-04.

1 P01 P15 P2 nota 8,0

07 · Design geral

A pergunta central respondida: sim, a fundação (backend modular, multi-tenant no core, CI com testes, docs excepcionais) é a certa para escalar. As dívidas pontuais que travavam a nota foram pagas e estão em produção; restam AC-07 (arquivos gigantes, parcial) e o teto estrutural da VPS única. Capacidade estimada em dezenas a poucas centenas de usuários simultâneos; escala em 3 estágios sem retrabalho.

2 P05 P12 P2 nota 7,5

08 · Lixo & limpeza

Relatório consultivo com a onda 1 já executada: o tmp/ foi higienizado (o dump real de 245MB e os segredos saíram do disco em 03/07). O repo versionado é pequeno e saudável (12,63MB de .git); ~99% dos 2,10GB do working tree é artefato local ignorado. Restam as ondas 2/3 do plano de limpeza.

1 P01 P11 P2 nota 7,5

09 · VPS

A VPS atual de ~7,8GB segura o presente: órfãs paradas, backup diário, monitoração e agora mem_limit/healthchecks live (03/07). O teto é estrutural — máquina única compartilhada com stacks alheias. Cenários dimensionados: hoje 4vCPU/8GB; 6–12 meses 6–8vCPU/16GB com automação separada; escala com PG gerenciado + Redis + CDN, condicionada a 4 pré-requisitos de software.

Lição no registro de falhas do ENGINEERING_PRINCIPLES: o deploy:fast embarca o working tree INTEIRO — antes de rodar, conferir as "Notas de Deploy" do doc canônico por passos manuais pendentes. O que continua valendo: nenhum serviço tem limite de memória (AC-11) e não há monitoração (AC-16).

Metodologia

Como esta série foi produzida, o que foi medido de verdade, o que é estimativa declarada e o que ficou fora do escopo.

Como foi feito

  • Exploração + verificação com medições reais no repositório local em 2026-07-02 (contagem de linhas, grep de padrões, leitura de código e configs).
  • Regra dura: nenhum número entra em página HTML se não estiver no fatos.json consolidado da sessão — formato pt-BR.
  • Estimativas são sempre marcadas como tal (capacidade de usuários, consumo por serviço e cenários de VPS no relatório 09).
  • Achados canônicos (AC-*) têm id, prioridade e evidência únicos em toda a série — a mesma dívida nunca aparece com id ou prioridade diferente em dois relatórios.

Limites do diagnóstico

  • Sem load test — a análise de performance é estática (código + configs), não medida sob carga.
  • Sem EXPLAIN — nenhum plano de query foi executado contra o banco.
  • Sem acesso à VPS nesta sessão — dados de produção vêm de auditorias anteriores documentadas.
  • Relatório 08 é 100% advisory — nada foi excluído; todo plano de limpeza depende de confirmação do dono.

Divergências corrigidas na verificação

O briefing inicial trazia estimativas que a medição desmentiu — os números finais foram conferidos, não chutados. Exemplos:

  • Linhas do front: briefing dizia ~46k; medição = 163.129.
  • Arquivos front acima de 450 linhas: briefing dizia 16; medição = 105.
  • Guard do dev secret: briefing dizia "sem guard"; medição = guard EXISTE (config.go:193-208), com ressalva de só disparar com APP_ENV exatamente "production".
  • tmp/: briefing dizia 7MB; medição = 254,18MB (245,35MB é um pg_dump real pré-rename).
  • "back;C" na raiz: briefing dizia 22MB; medição = diretório VAZIO (0 bytes) — resíduo de comando mal-escapado.
