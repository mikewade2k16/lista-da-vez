# AGENTS

## Escopo

Estas instrucoes valem para `web/app/components/cardapio/` (painel `/cardapio`). Nome de EXIBICAO do modulo = **Presence** (menu, header, breadcrumb). O id interno segue `cardapio` (rotas `/v1/cardapio`, schema do banco, workspace `cardapio_web`, pastas) — a renomeacao de 2026-06-19 foi SO de rotulo. A palavra "cardapio" ainda vale para o MENU de produtos do estabelecimento (uma parte do modulo). Cada entidade e um "estabelecimento" (config de um site inteiro, nao so o cardapio).

## Responsabilidade

Painel de gestao dos cardapios online (restaurantes). CRUD de restaurante, categorias, produtos
(variacoes/adicionais/galeria), avaliacoes, dominios e pedidos. O front PUBLICO (site estatico que o
visitante acessa) e outro repo: este painel so administra os dados via API do painel.

Doc canonico do modulo: `docs/cardapio/PLANO_MODULO_CARDAPIO.md` (contrato em §4, front em §5).

## Arquitetura

- **Pages** (`pages/cardapio/`): orquestradores finos.
  - `index.vue` -> `CardapioListWorkspace`.
  - `[id].vue` -> `CardapioEditorWorkspace` (recebe `restaurantId` e `accountId` da rota; `?account=`
    so para `platform_admin` abrindo cardapio de OUTRO cliente).
- **Store** (`stores/cardapio.ts`): unica fonte de dados. Lista lean, restaurante ativo + catalogo +
  dominios + zonas de entrega, pedidos paginados. `X-Account-Id` e injetado pelo `createApiRequest`
  (account ativa) — nao passar manualmente. Para `platform_admin` abrindo restaurante de OUTRA
  account, o `accountId` vai na query de TODAS as chamadas do editor: `loadRestaurant(id, accountId)`
  seta `scopeAccountId` e `withScope()` anexa `?accountId=`; o backend prioriza o query sobre o header
  (`scopedAccountID`). Vazio = account ativa (nao-admin ou agencia). Na LISTA o `scopeAccountId` esta
  vazio (e do editor); por isso a edicao/exclusao inline usa `patchRestaurantScoped(id, accountId, body)`
  e `deleteRestaurantScoped(id, accountId)`, que recebem o `accountId` da PROPRIA linha e o anexam via
  `withScopeFor()` so naquela chamada — senao a alteracao de um restaurante de outra account cairia na
  account ativa e daria 404. As versoes scoped atualizam a projecao lean da lista (nao o `restaurant`
  do editor). `patchRestaurant`/`deleteRestaurant` (sem suffix) seguem para uso do editor.
- **Types** (`domain/cardapio/types.ts`): port EXATO do contrato (camelCase). Dinheiro SEMPRE em
  centavos inteiros (`...Cents`). Helpers `formatCurrency`/`formatCents`/`parseCents`/`slugify` e os
  labels pt-BR de status/tipo de pedido vivem aqui.
- **Composables**:
  - `useCardapioEditor.ts`: estado + dirty-check + salvamento da secao Dados, e upload de midia. O
    `DadosForm` inclui `segment`, redes (`facebook`/`youtube`), `address` completo
    (`number`/`complement`/`reference`), `settings.payment` e estatisticas
    (`googleAnalyticsId`/`facebookPixelId`/`customHeadHtml`). NAO envia `slug` nem `theme` (o theme e
    salvo so pela secao Aparencia, para nao sobrescrever).
  - `useCardapioProductForm.ts`: conversao Product <-> form e montagem do payload PATCH do produto.

## Regras

- Centavos no modelo, `R$` na tela — sempre via `CardapioMoneyInput`/`formatCurrency`/`parseCents`.
- Tokens do design system (`omni-tokens.css`); nunca hex. BEM `.cardapio-x__el--mod`.
- Raiz de pagina rola: `flex:1; min-height:0; overflow-y:auto`.
- Acoes com spinner/disable + toast (`useUiStore().success/error`); confirmacao destrutiva via
  `useUiStore().confirm`. Estados vazios orientativos.
- Filtro por cliente e o `accountId` na criacao so existem para `platform_admin`; demais papeis
  operam na propria account (o backend resolve o escopo).
- **Shape do body no PATCH** (`ReadJSON` usa `DisallowUnknownFields`): (1) NUNCA enviar campo que o
  Input do back nao tem — `slug` no PATCH de restaurante (imutavel) e `id` em variacao/adicional
  (replace-all) dao `400 "Body invalido"`. (2) `CategoryInput`/`ProductInput`/`ReviewInput` sao
  full-replace (nao-ponteiro): todo PATCH (inclusive toggles de `isActive`/`isAvailable`/`isHighlight`
  e reordenacao) manda o OBJETO COMPLETO + o campo alterado, senao zera o resto e da `400 "Dados
invalidos"`. O toggle de disponibilidade do produto busca o produto completo antes (lista e lean).
  So `UpdateRestaurantInput` e `UpdateDeliveryZoneInput` sao parciais (pointer-based) — toggle/edicao
  de zona pode mandar so o campo alterado.
- **Fase 2 (paridade lojatop)**:
  - **Pagamento** (`settings.payment`, WS-B): sub-objeto informativo do `settings`
    (`{cash, debit:{accepted,brands[]}, credit:{accepted,brands[]}, pix, ticket, other}`). Salvo no
    body COMPLETO do save de Dados (settings inteiro). Bandeiras: string por virgula <-> array
    (`parseBrands`/`formatBrands`). NAO entra no checkout.
  - **Tema RICO** (`restaurant.theme`, WS-D): a secao Aparencia e a UNICA dona do theme. Shape rico
    `{base, mode, colors{background,surface,text,accent,border}, fonts{display,body}, radius}`
    (`RestaurantTheme`/`normalizeTheme`). Listas curadas em `types.ts`:
    `CARDAPIO_THEME_PRESETS` (tavola/brasa, cada um com tema completo), `CARDAPIO_THEME_COLOR_FIELDS`
    (5 cores + hint), `CARDAPIO_THEME_FONTS` (familias do TAVOLA), `CARDAPIO_THEME_MODES`,
    `CARDAPIO_THEME_RADII`. Salva via PATCH parcial `{theme}` (jsonb livre). As 5 cores sao HEX
    escolhidos pelo usuario (DADO), unica excecao a regra "nunca hex". `saveDados` NAO envia `theme`.
  - **Back-compat do tema**: `normalizeTheme` MIGRA o shape antigo `{base,accent,font,mode}` na leitura
    — `accent` antigo vira `colors.accent`, `font` antigo vira `fonts.display`, o resto herda do preset
    da `base`. Nada que ja foi salvo quebra; ao salvar de novo, grava o shape rico.
  - **Mapa semantico -> tokens** (o que cada chave PINTA no site publico/TAVOLA; fonte unica em
    `THEME_SEMANTIC_MAP`, `types.ts`): `colors.background` = fundo da pagina; `colors.surface` =
    cards/blocos; `colors.text` = texto; `colors.accent` = destaque (botoes, precos, links, primaria);
    `colors.border` = linhas/contornos; `fonts.display` = titulos; `fonts.body` = corpo; `radius` =
    raio dos cantos; `mode` = esquema claro/escuro. O painel expoe o mesmo mapa como CSS vars `--prev-*`
    no preview (`themeToPreviewVars`); o TAVOLA aplica o equivalente do seu lado.
  - **Campos novos do restaurante** (WS-C): `segment`, `facebook`, `youtube`, `googleAnalyticsId`,
    `facebookPixelId`, `customHeadHtml`; `address` ganha `number`/`complement`/`reference`. GA/Pixel
    sao seguros (so IDs). `customHeadHtml` = HTML livre injetado no site = XSS: editavel SO por
    `platform_admin` (gate em `CardapioDadosEstatisticas.vue` com `LegacyMarker`); demais papeis
    veem read-only e reenviam o valor atual inalterado.
- Admin abrindo restaurante de outro cliente: o editor leva o `accountId` na query (lista/criacao ->
  `/cardapio/{id}?account=<accountId>`). Sem isso o GET cai na account ativa (`X-Account-Id`) e da 404
  quando o restaurante e de outra account. O default "Agencia" no modal mantem o caso comum na account
  ativa, onde nem precisa do `?account=`.
